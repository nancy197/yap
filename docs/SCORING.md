# YAP scoring v1

## Data source

The source of truth is the [`social-kv/1` standard](https://api2.near.social/standard.md), which defines writes to receiver `social` through `__fastdata_kv`. The [near.social API](https://api2.near.social/api.md) serves derived feeds, but its cursor lists are not a complete historical epoch export. The [FastData KV API](https://docs.fastnear.com/fastdata/kv/history-by-account) provides `POST https://kv.{main|test}.fastnear.com/v0/history/social` across every predecessor. A request with `{"limit":200,"asc":false,"include_metadata":true}` returns `entries` and an opaque `page_token`; the token must be sent back with the same filters until absent. Each entry includes predecessor, key, value, block height and nanosecond block timestamp. With metadata it also includes receipt, action and transaction IDs. The `/v0/all/{predecessor_id}` route lists only *latest* values for one writer, and `/v0/latest/social` omits history; neither can enumerate every epoch write.

The KV history API has **no block-height or timestamp filter**. The indexer therefore exhausts the `social` history, filters the half-open interval `[fromMs,toMs)` using integer nanosecond timestamps, and replays all earlier writes to obtain end-of-epoch posts and the follow graph. Mainnet reads are always read-only. The live API returned 3,423 rows during the 2026-11-07 scan; the seven-day sample contained 273 writes. `block_timestamp` is quoted before JSON parsing so its u64 nanoseconds do not lose precision in JavaScript. The response does not expose the standard's `order_id`; for conflicting writes of the same key in one block the replay uses the documented newest-first history order, with a stable receipt-ID fallback for input lacking source order. Cross-key order within one block does not affect last-write-wins state.

Valid account IDs, post IDs, post fields, media, replies, object-valued edges, tombstones and original created times follow `social-kv/1`. Invalid latest values make an entity absent. A post edited during an epoch retains its first valid creation time; it earns post score only in the creation epoch. Likes and reposts count if their latest write in the epoch is an object. Follows are the object-valued graph state at epoch end. The indexer stores **all** raw epoch writes plus derived end state in `data/epochs/<network>/<e>.json`; `dataHash` is SHA-256 of canonical JSON with sorted object keys and stable array order, omitting the `dataHash` field itself. The CLI accepts `--out` for custom ranges. For production epochs the caller supplies `--epoch <u32>` with the contract epoch number relative to genesis; the default is the Unix day index for ad hoc previews.

The current public API provides no historical YAP stake snapshot; stake balances are a separate explicit input to `score`. Before an on-chain report, the scorer service must obtain whole-epoch stake snapshots from the contract's chain history. A missing stake input means zero stake, as in the read-only sample.

## Fixed-point rules

All score values are signed decimal strings in units of `1e-6`; YAP amounts and stake inputs are integer strings in raw 18-decimal token units. Arithmetic uses `bigint` and floors every division. PageRank uses a mass of `1e12`, 40 iterations, damping `85/100`, and teleport proportional to `1 + sqrt(YAP staked, represented at 1e-6 precision)`. Integer division remainders go to accounts in ascending account-ID order. `rank_norm` is rank divided by the maximum rank. Eligible smart accounts have at least `minFollowers` active followers; the highest `ceil(smartPct * eligible / 100)` PageRank positions are smart, with account ID resolving ties. Default parameters are 20%, 3 followers and 10 posts.

For an aged account `u`, engagement weight is `rank_norm(u) × (1 + 0.5 × isSmart(u)) × (1 + log10(1 + yapStake(u)))`, times 1 for a like, 2 for repost, 3 for a qualifying reply, and 4 for a qualifying quote. Reply and quote labels must be at least 2. Self actions and actions from an account whose first valid write is in this epoch are ignored. Actions sort by actor, target post and action type before the first three per actor–author pair are taken. This makes the cap independent of input order.

For post `p`, `post_score = Q[q] × (1 + ln(1 + sumWeights))`, with `Q = [0, 0.25, 1, 2]`. Natural log and base-10 log use a deterministic integer series in `scoring/src/fixed.ts`; no floating-point score is serialized. An author's Yap score is the sum of their ten highest post scores, with key order breaking ties. Zero smart followers and zero stake halve that sum. `attention` is the sum of final Yap scores. Yapper allocation is split pro rata by final Yap score, with leftover atomic units assigned in account-ID order.

A topic is a normalized hashtag, cashtag or mention. Its mindshare is the sum of post scores that mention it divided by **all** epoch post scores; a post can contribute to multiple topics. Tiers use the current plus up to 29 preceding epoch Yap scores: top 1% Inner Circle (4), top 10% Gold (3), top 30% Silver (2), then Bronze (1) for positive trailing score; None is 0. Positive-score yappers are ranked by score, then account ID. Arenas filter to their topic, apply the same best-ten and sybil rules, require the requested minimum tier, and split their per-epoch pool pro rata.

### Worked example

A new epoch has one normal (`q=2`) post by `alice.near`, no engagement, no stake, and no smart followers. Its post score is `1,000,000 × (1 + ln(1)) = 1,000,000`. Sybil damping makes Alice's Yap score `500,000` (0.5 YAP score units), so attention is `500,000`. If her post contains `#near`, that topic's mindshare is `1,000,000` (100%). With a 1,000 atomic-unit yapper pool, Alice receives 1,000 units. A 100-unit `#near` arena that permits Bronze also pays her 100 units. These values are asserted in the Vitest suite.

## Merkle and verification

Yapper leaf: `SHA-256(0x00 || Borsh(u32 epoch, String account, u128 amount, u64 score, u8 tier))`. Arena leaf: `SHA-256(0x01 || Borsh(u32 arenaId, u32 epoch, String account, u128 amount))`. Borsh strings have a u32 little-endian UTF-8 byte length; all integers are little-endian. Nodes are `SHA-256(0x02 || min(childA,childB) || max(childA,childB))`, comparing the 32-byte hashes lexically. Leaves sort by account ID. Odd nodes duplicate themselves. The empty root is 32 zero bytes. `scoring/test-vectors.json` contains independently generated leaf, node, root and proof bytes.

A published epoch URI contains `dataset.json`, `labels.json`, `stakes.json` and `params.json`. `verifyUri` loads those files and recomputes hashes, scores, attention, global root and arena roots. `verifyOnChain` also reads `get_epoch(e)` from the token RPC. Labels are an explicit JSON map of post key to quality `0..3`; their hash is SHA-256 of sorted-key canonical JSON. The read-only preview uses `mockLabels.ts`, clearly marked **SIMULATED**, and must never be submitted as a TEE-attested label file.
